# 证据、分歧与裁决协议

- 版本：v2.0.0 (2026-08-12)
- 适用：Architect、Coder 以及独立 reviewer
- 原则：文件记录是跨 session 的权威状态；实时消息只作通知

## 1. 双真相模型

### 目标真相

目标行为按以下优先级确定：用户在本轮记录的决定、用户批准的验收标准、批准的 PRD/需求文档、经批准且不冲突的技术方案与执行计划。它们回答“完成后系统必须做什么”。

### 当前真相

当前状态必须由仓库证据确定：已检出的源码签名和调用关系、测试/构建/静态检查输出、配置、Schema、迁移、依赖元数据、项目内用法和必要的版本历史。注释、README、历史方案和委托扫描摘要只能作为辅助证据。

任务文档、技术方案和执行计划是待核实的执行指令，不是不可质疑的当前事实。当前代码不能静默覆盖批准的产品目标；产品目标也不能假设不存在的 API 或数据流已经存在。

## 2. 证据等级与锚点

每个重要决策或分歧至少记录一个证据锚点：Coder 环境可访问的原生绝对路径、稳定符号/签名/测试/配置键/Schema 对象或只读命令、观察事实、证据状态。

| 状态 | 含义 | 可否直接用于裁决 |
|------|------|------------------|
| `DIRECT` | 直接读取当前源码、配置、Schema 或依赖元数据 | 可作为证据，裁决者仍需独立复核关键项 |
| `REPRODUCED` | 已运行只读命令、构建、测试或检查并记录结果 | 可作为证据，保留命令与结果摘要 |
| `INFERRED` | 根据命名、邻接调用或历史资料推断 | 不可单独用于裁决 |
| `UNVERIFIED` | 未访问、访问失败或路径不可达 | 不得写成事实 |

行号只是辅助定位；符号、签名、调用关系、测试名、Schema 对象、配置键、依赖版本和可复现命令输出优先。委托扫描摘要永远不能单独支撑 `ARCHITECT_DECIDED`。

## 3. 执行模式

每个实现单元必须声明且只能声明一种模式：

| 模式 | 用途 | Coder 行为 |
|------|------|------------|
| `BOUNDED_AUTONOMY` | 默认业务实现 | 在允许文件、契约、依赖、持久化和验收边界内自主选择局部实现 |
| `EXACT_CHANGE` | 安全常量、协议文本、迁移、生成兼容层和 v1.x 任务 | 按指定内容精确修改；锚点不符必须停下并开分歧单 |
| `INVESTIGATE_FIRST` | Architect 尚未完全核实的可访问区域 | 先收集指定证据；只有发现符合假设时才继续，否则暂停并开分歧单 |

## 4. 受约束自主边界

在 `BOUNDED_AUTONOMY` 内，Coder 可以选择私有 helper、内部控制流、等价校验/错误处理、项目内既有工具、测试夹具和局部重构，前提是不改变可观察契约和本单元不变量。

Coder 必须升级后才能：修改 public 方法/端点/事件/DTO/异常或序列化契约；改动允许文件之外的文件；新增或替换未声明的服务、SDK、依赖或数据源；改变 Schema、迁移、事务、持久化、留存语义；改变用户可见行为或验收标准；替换批准的架构；扩大 commit、验证、归档或部署范围。

## 5. 分歧分类

| 类型 | 默认处理 |
|------|----------|
| `LOCAL_CHOICE` | Coder 在自主边界内决定并写决策摘要 |
| `FACT_MISMATCH` | 暂停受影响分支，Architect 独立核实 |
| `PLAN_AMBIGUITY` | Architect 按已批准方案裁决；方案未覆盖则升级 |
| `DESIGN_CONFLICT` | 返回 superpowers 修订方案与执行计划 |
| `PRODUCT_AMBIGUITY` | Architect 整理证据与选项后询问用户 |
| `CONTRACT_OR_SCOPE` | 必须询问用户 |
| `SAFETY_RISK` | 停止相关工作，必须询问用户 |

## 6. 依赖感知暂停

Coder 发现事实不符、契约不明、依赖未声明或风险升级时，必须暂停受影响单元及其下游依赖，并在分歧单中记录原因。只有能够以证据证明与分歧无依赖的单元才可继续，并记录独立性依据。不得用“先做完再说”绕过暂停。

## 7. 分歧单必填字段

分歧单必须包含：唯一 ID、类型、发现任务版本、影响单元和下游单元、任务主张、代码事实、证据锚点、复现命令与结果、Coder 分析摘要、建议、暂停/可继续范围、Architect 独立核实、最终分类、裁决者、裁决结果、纳入的新任务版本、恢复范围和关闭条件。

## 8. 裁决状态机

```text
DISCOVERED
  → EVIDENCE_READY
  → ARCHITECT_VERIFYING
  ├→ ARCHITECT_DECIDED
  ├→ USER_INPUT_REQUIRED → USER_DECIDED
  └→ PLAN_REVISION_REQUIRED → superpowers 修订并获批
  → TASK_UPDATED
  → RESUMED
  → CLOSED
```

实时消息不能替代状态文件。影响交付的分歧没有进入 `CLOSED` 前，任务不得报告 `COMPLETED`。

## 9. Architect 核实与裁决

Architect 必须重新读取决定性源码、配置、Schema 或复现命令，不得只接受 Coder 或弱模型摘要。Architect 可裁决事实不匹配和自主边界内选择；产品语义、公共契约、范围、依赖、持久化和重大风险必须询问用户；设计变化必须回到 superpowers，不得在 cdel 内自创替代方案。裁决后先更新任务版本和决策记录，Coder 读取新版本后才可恢复。

## 10. 用户交互边界

只有涉及产品含义、验收标准、公共契约、范围、依赖、持久化、上线或材料风险时才打断用户。提问必须带证据、影响范围和可选决策；局部实现选择不升级用户。

## 11. 任务版本与恢复门

任务文档、分歧单和交付报告都使用 `vN` 版本。口头裁决无效；恢复必须读取包含分歧 ID、明确裁决和恢复范围的更新任务版本。已派发的 v1.x 文档不静默迁移，按 `EXACT_CHANGE` 执行。

## 12. 跨平台绝对路径

实际派发文档不得包含 `~`、环境变量、相对路径、`file://` URI、未解析模板变量或混合路径分隔符。Architect 必须根据 Coder 环境生成并验证原生绝对路径；操作系统或共享文件系统不明确时先询问用户。支持 macOS/Linux、Windows 和 WSL 的原生路径表达。

## 13. 兼容 v1.x

旧任务继续使用原有文件清单、动作语义和自测要求，但在 v2 术语中视为 `EXACT_CHANGE`。只有用户或 Architect 明确生成 v2 新版本后，任务才迁移到 `BOUNDED_AUTONOMY` 或 `INVESTIGATE_FIRST`。
