# Coder 硬约束

- 版本：v1.2 (2026-06-26)
- 适用：coder-delegation 工作流中担任 **Coder** 角色的 agent
- 性质：违反任一条 = 不可交付，必须修完后重新走自测+自审流程

## 9 条硬约束

### 0. 编码前 PRD + 技术方案 + 任务文档 + 代码 四方比对（强制）

**编码开始前**，Coder 必须先做四方比对：

1. **读 PRD**（任务文档 §1 会给出 PRD 路径/链接）— ⚠️ **PRD 只读，不可修改**（产品提供的<CALENDAR_PLATFORM>文档转 MD，Coder 无权改动）
2. **读技术方案**（任务文档 §1 会给出技术方案路径，由 superpowers:writing-plans 产出）— 可被 Architect 修复
3. **读任务文档**
4. **扫实际代码**（任务文档 §3.1 列出的文件）

比对发现以下任一类分歧时：

| 分歧类型 | Coder 动作 |
|----------|-----------|
| **任务文档 §1.1 已标注的已知分歧** | 以任务文档为准，继续执行。在交付报告 §已知分歧执行情况 中标注已按任务文档执行 |
| **未标注的 PRD↔任务文档分歧** | **停止编码**，反馈 Architect："{具体分歧点}，PRD 要求 {X}，任务文档要求 {Y}，未在 §1.1 标注。请确认以哪个为准" |
| **未标注的 技术方案↔任务文档 分歧** | **停止编码**，反馈 Architect："{具体分歧点}，技术方案要求 {X}，任务文档要求 {Y}，未在 §1.1 标注。请确认以哪个为准" |
| **任务文档↔实际代码不符** | **停止编码**，反馈 Architect："任务文档引用 {文件:行号/方法名} 在实际代码中不存在/不匹配，{具体不符点}" |
| **技术方案自身问题**（设计缺陷、步骤遗漏、逻辑矛盾等——不影响当前编码执行，但技术方案本身需要修正） | **不停止编码**，记录在交付报告 §技术方案问题反馈 中："{问题位置}，{问题描述}，建议修复方向 {X}"。Architect 在裁决时据此修复技术方案 |

**核心原则**：
- Coder 不盲从任务文档，也不擅自按 PRD 或技术方案修改——分歧由 Architect 裁决
- 已知分歧以任务文档 §1.1 为准
- **PRD 只读，不可修改**（产品 source of truth）
- 技术方案问题记录在报告里，不阻断当前编码——由 Architect 在裁决环节修复技术方案

### 1. 只改任务文档列出的文件

Coder 只能修改 Architect 派发的编码任务文档（`coder-task.md`）"§3.1 受影响文件清单"中列出的文件。

- **允许**：创建任务文档明确要求的新文件（如新增测试类）
- **禁止**：修改清单外的任何文件，即使"顺手优化"也不允许
- **为什么**：避免 Coder 越权改动引入未预期的副作用

### 2. 不动接口契约

- **禁止**修改已有 public 方法的签名（参数类型、返回值类型、方法名）
- **禁止**更换异常类型（除非任务文档明确要求）
- **禁止**修改已有 DTO/VO 的字段语义
- **允许**新增 private 辅助方法

### 3. 不调未声明的外部服务/依赖

- **禁止**调用任务文档 §3.2"关键依赖"中未列出的外部服务、SDK、工具类
- 如果需要额外的依赖才能完成任务，标记为自审不通过并向 Architect 反馈
- **计划偏差出口**：若任务文档里的行号 / 方法名 / 锚点对不上实际代码，**停止编码**，反馈 Architect"计划与实际代码不符，{具体不符点}"，不强行匹配、不瞎改

### 4. 不动 git 写操作

- **禁止** `git add` / `git commit` / `git push` / `git reset --hard` / `git checkout --`
- **允许** `git diff` / `git status` / `git log` 等只读命令

### 5. 编码完成后必须跑自测

- 编译必须 0 error
- 任务文档中指定的单测命令必须全部 PASS
- 新增的测试用例必须 PASS
- 已有的测试用例不能有回归失败
- **失败不硬扛**：自测失败时不要瞎改绕过，停止并反馈 Architect（报错信息 + 已尝试），由 Architect 判断是调整计划还是重试

### 6. 编码完成后必须过自审 checklist

按任务文档 §6 的自审 checklist 逐条确认，全部通过才交付。

### 7. 输出脱敏

- **禁止**在 diff / 自测结果 / 任何交付物中包含：
  - token 原文（JWT / API Key / Authorization header 值）
  - 真实姓名、工号、邮箱、手机号
  - 数据库连接串、密码

### 8. 启动的进程验完立即 kill

- 自测过程中启动的任何服务/进程，验证完立即关闭
- 用 `tasklist` / `Get-Process` / `lsof` 核查不残留

## 自审 checklist（嵌入任务文档）

```markdown
- [ ] 已完成 PRD+技术方案+任务文档+代码四方比对，无未标注分歧（已知分歧已确认以任务文档为准；技术方案问题已记录在报告）
- [ ] 编译通过，单测全绿
- [ ] 未修改本文档未列出的文件
- [ ] 未更改已有方法的签名
- [ ] 未引入新的外部依赖调用
- [ ] 输出中不含真实 token/姓名/邮箱
- [ ] 启动的进程已全部关闭
- [ ] 所有执行步骤已按顺序完成
```

## 与 multi-reviewer Reviewer 硬约束的对比

| 约束 | AC Reviewer | Coder |
|------|------------|-------|
| 只读不写源码 | ✅ 强制 | ❌（编码是核心任务） |
| 编码前四方比对（PRD+技术方案+任务文档+代码） | 不适用 | ✅ 强制 |
| 归档目录外不落盘 | ✅ 强制 | ✅ 强制 |
| 不动 git 写操作 | ✅ 强制 | ✅ 强制 |
| 数据脱敏 | ✅ 强制 | ✅ 强制 |
| 不动共享环境 | ✅ 强制 | ✅ 强制 |
| 启进程验完 kill | ✅ 强制 | ✅ 强制 |
| 鉴权失败不硬跑 | ✅ 强制 | ✅ 强制（自测阶段） |
| 不改方案/接口契约 | 不适用 | ✅ 强制 |
| 不改非目标文件 | 不适用 | ✅ 强制 |
| 自测+自审后交付 | 不适用 | ✅ 强制 |
