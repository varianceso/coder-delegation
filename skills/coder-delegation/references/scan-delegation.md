# 代码扫描委托规范

- 版本：v1.2 (2026-06-26)
- 适用：Architect 角色在 Step 2 生成 Coder 任务文档前，需要理解大量代码时
- 目的：把"代码扫描"这种机械工作委托给弱模型，Architect 只消费摘要做机读化判断，降低强模型 token 成本

## 核心思想

Architect 机读化（把 superpowers 产出的技术方案/执行计划转成 Coder 任务文档）时需要理解代码现状。扫描代码本身是"机械工作"（读文件、理调用链、提取签名），不是"判断工作"。把扫描委托给弱模型出摘要，Architect 只消费摘要 + 做机读化判断，能显著降本。

> ⚠️ **委托扫描的摘要不能替代 Architect 的核实闭环**。弱模型摘要可能漏关键调用链/跨仓路径/实际 API 用法；Architect 消费摘要后仍必须执行 §2b 核实闭环（见 SKILL.md Step 2），对跨仓调用链、组件 API、代码引用做扫码确认。摘要告诉你"大致什么在什么地方"；核实保证"每个事实点都真实存在"。

## 何时委托（触发条件）

| 改动规模 | 是否委托 | 理由 |
|----------|----------|------|
| 小改动（1-2 个方法、单文件） | ❌ 不委托，Architect 直接读 | 委托本身有协调成本（写扫描任务、整合摘要），改动小时不值得 |
| 大改动（跨模块 / 需理解调用链 / 数据流 / 多文件影响面） | ✅ 委托弱模型扫描出摘要 | 强模型直读全量代码 token 成本高；摘要降本明显 |

**判断口径**：改动涉及 ≥3 个文件，或需要理解跨类/跨模块调用关系才能机读化 → 委托。

## 能力探测（先探后选）

Architect 先探测当前环境有无 workflow 子 agent 能力，有则自动用（路径 A），无则询问用户（路径 B）。探测按以下顺序，命中即停：

1. **查当前会话可用工具列表**是否含子 agent / Task / Workflow / dispatch_subagent 类工具（如 Claude Code 的 `Workflow`/`Agent` 工具）
2. **查 available_skills 列表**是否含 workflow 类 skill
3. **查运行时特征**：Claude Code 支持 workflow；Codex/opencode 等 CLI 通常无内建子 agent 并行能力

- **探测到有** → 走路径 A
- **探测到无 / 不确定** → 走路径 B（询问用户），不静默假设

## 路径 A：workflow 子 agent 扫描

Architect 启动 workflow，派弱模型子 agent 并行扫描，汇总摘要。

- **扫描任务**：明确告诉子 agent 扫描范围（哪些模块/包）、要提取什么（见"摘要结构"）
- **并行**：多个子 agent 各扫一块，Architect 汇总
- **Architect 只做**：整合扫描结果、做机读化判断（不自己读全量代码）
- **摘要落盘**：汇总后写到 `<repo>/.claude/<slug>/codebase-scan-<name>.md`（用 `templates/codebase-scan-summary.md` 模板）

**路径 A 失败兜底**（任一触发则降级）：
- workflow 启动失败 / 子 agent 不可用 → 自动转路径 B（询问用户）
- 子 agent 扫描部分失败（某块没扫到）→ 对失败块补扫；补扫仍失败则该块标"未覆盖"并在摘要附录说明
- 汇总摘要缺 5 段任一段（质量门）→ 要求子 agent 补齐该段；补不齐则该段标"待 Architect 核实"，Architect 对该段直读代码补全
- 用户环境不支持并行 → 串行扫描或转路径 B

## 路径 B：询问用户用其他弱模型 session 扫描

无 workflow 能力时，Architect 询问用户：

```
本次改动涉及 {N} 个文件 / 跨 {模块}，需要理解代码现状才能机读化。
当前 session 无 workflow 子 agent 能力，建议用其他弱模型 session（如 Codex + 弱模型）扫描代码出摘要文档：

扫描范围：{模块/包路径}
要提取：模块职责 / 关键类签名 / 调用链 / 数据流 / 改动影响面
摘要模板：<repo>/skills/coder-delegation/templates/codebase-scan-summary.md

是否要这样做？摘要产出后交回，我基于摘要做机读化。
```

- 用户同意 → 等待摘要文档交回，Architect 基于摘要机读化；摘要缺段则要求用户补扫或 Architect 直读补全
- 用户拒绝 → Architect 自行直接读代码（接受较高 token 成本）或建议缩小改动范围

## 摘要结构（面向设计决策）

摘要**不是**"这个文件有哪些类"的清单，而是面向强模型做机读化判断所需的结构化信息。固定 5 段（模板见 `templates/codebase-scan-summary.md`）：

| 段 | 内容 | 为什么需要 |
|----|------|-----------|
| 模块职责 | 各相关模块/包一句话职责 | Architect 判断改动影响哪些模块 |
| 关键类签名 | 相关类/方法签名 + 所在路径 | Architect 机读化时定位精确 |
| 调用链 | 改动涉及的调用关系（谁调谁） | Architect 判断改动是否会破坏调用方 |
| 数据流 | 数据怎么流转/持久化 | Architect 判断数据一致性影响 |
| 改动影响面 | 改动可能波及的下游/测试 | Architect 列受影响文件清单 |

**关键**：弱模型摘要漏了关键调用链，强模型基于残缺摘要机读化会埋雷。所以摘要模板强制覆盖这 5 段，弱模型不能随意省略。摘要附录含"5 段完整性自查"checkbox，弱模型交付前自检。

### 跨仓调用链特别要求

涉及前端→后端、CLI→后端、服务间调用等跨仓场景时，摘要 §3 调用链必须包含：

- **实际调用路径**（凭代码核实，不凭命名推断）：Controller → Service → Handler 完整链路
- **接口适配层**：DTO/Req 类名、API 端点路径
- **常见陷阱标注**：如"CLI 不走通用 CRUD 接口，走 agent 专属路径"

### 框架/组件 API 用法特别要求

扫描涉及前端框架组件（如 antd、Element UI）时，摘要 §2 关键类签名必须包含：

- **项目内现有用法的精确锚点**（file:line），含 API 参数名/回调签名
- **常见 API 差异标注**：如项目用 `autoSize`（首字母小写 s）而非 `autosize`、用 `onChange(e => e.target.value)` 而非 `onChange(val)`

## 落盘与复用

- 摘要落盘：`<repo>/.claude/<slug>/codebase-scan-<name>.md`
- **跨会话复用**：后续会话/同类改动若涉及同一模块，先读已有摘要，只扫改动相关增量，不全量重扫
- **增量扫描判定机制**：
  - 已有摘要附录记录"扫描时间 + 覆盖文件列表"
  - 新改动用 `git diff --name-only` 取变更文件，与摘要覆盖列表比对
  - 变更文件都在覆盖内且数量少 → 只补扫变更部分，更新摘要的"扫描时间"和"覆盖列表"
  - 变更超出覆盖范围或差异大（如 ≥30% 文件变动）→ 触发全量重扫，旧摘要归档标注"已过时"
  - 无法 git diff（无版本控制）→ 询问用户是否全量重扫

## 与 superpowers 的边界

- 代码扫描委托是 **cdel 机读化阶段独有**的能力：cdel 在 Step 2 把 superpowers 产出的方案/执行计划机读化为 Coder 任务文档时，用它降本
- superpowers:writing-plans 阶段若也需理解代码，由 superpowers 自己的流程决定如何扫描——cdel 不把本机制宣称为 superpowers 的能力，也不介入 superpowers 阶段
- 简言之：**cdel 用本机制做机读化前的代码理解；superpowers 阶段的代码理解不归 cdel 管**
