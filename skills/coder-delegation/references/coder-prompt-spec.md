# Coder 编码任务文档规范

- 版本：v1.2 (2026-06-26)
- 适用：Architect 角色生成 Coder 编码任务文档时的格式与质量规范
- 读取方：Coder（弱模型 agent）

## 文档定位

Coder 编码任务文档是一份**独立、自包含、可执行**的 `.md` 文件。
Coder agent 加载本文件后应具备完整上下文，不需追问、不需补全设计，直接开干。

## 质量要求

| 维度 | 标准 |
|------|------|
| **自包含** | Coder 不需要读任何其他文件即可理解全部任务 |
| **精确** | 文件路径、方法名、行号、代码块无歧义 |
| **可执行** | 自测命令可直接复制粘贴运行，无需调整 |
| **防偏离** | 硬约束明确，Coder 无法误解"什么能做/什么不能做" |
| **可核实** | 所有代码引用旁标核实状态（✅/⚠️），Coder 可据此判断引用可靠性 |

## 必需章节

| 章节 | 必要性 | 说明 |
|------|--------|------|
| §1 任务概述 | 必须 | 一句话 + 一段自然语言 + PRD 路径 + 技术方案路径 |
| §1.1 已知分歧 | 条件必须 | PRD↔技术方案有分歧时必填，无分歧可省略 |
| §2 硬约束 | 必须 | 固定 9 条（含第 0 条四方比对） + 本次特有约束 |
| §3 上下文 | 必须 | 受影响文件清单 + 关键依赖 + 字段透传链路（条件） |
| §4 执行步骤 | 必须 | 每步精确到文件/定位/动作/代码，旁标核实状态 |
| §5 自测要求 | 必须 | 编译命令 + 单测命令 + 验收标准 |
| §6 自审 checklist | 必须 | 8 条固定 checklist |
| §7 输出要求 | 必须 | 报告落盘路径 + 交付内容 |

## 各节编写要点

### §1 任务概述

- 第一句：一句话说清"做什么"
- 第二段：简要交代"为什么"，1-3 句即可
- 不要写技术方案的分析过程，只写"要达成什么"
- **必须注明 PRD 来源和技术方案来源**：
  - `PRD：<<CALENDAR_PLATFORM>文档转 MD 路径/链接>（只读，不可修改）`
  - `技术方案：<superpowers:writing-plans 产出的 tech-design 文档路径>`

### §1.1 已知分歧（条件必须）

> **触发条件**：PRD 与技术方案/执行计划存在有意分歧时必填。无分歧可省略本节。

Architect 在机读化过程中对比 PRD 与技术方案，发现的**有意分歧**必须在本文档显式标注，防止 Coder 按 PRD 擅自修改。

```markdown
## 1.1 已知分歧（以本文档为准，勿按 PRD 改）

| # | 分歧点 | PRD 原文 | 本文档要求 | 原因 |
|---|--------|---------|-----------|------|
| D1 | 字段命名 | `departmentResponsibility` | `deptResponsibility` | 技术方案统一命名，已与产品确认 |
| D2 | 字段长度 | 1300 | 2000 | 技术评估后扩大，兼容历史数据 |
| D3 | F-003 问号 icon | 悬浮问号触发 popover | placeholder 文本"（可选）" | 本期降级实现 |
```

**Coder 行为**：已知分歧以本文档为准。交付报告 §已知分歧执行情况 中逐条标注"已按任务文档执行"。

### §1.2 降级项标注（条件必须）

> **触发条件**：技术方案相对 PRD 有降级实现时必填。

```markdown
## 1.2 降级项

| # | PRD 功能点 | PRD 要求 | 降级实现 | 影响 |
|---|----------|---------|---------|------|
| DG1 | F-003 帮助提示 | 悬浮问号 + popover 展示说明 | placeholder 文本替代 | UI 交互降级，功能不受影响 |
```

**Coder 行为**：降级项按降级方案实现，在交付报告中标注"已按降级方案实现"。

### §2 硬约束

- 固定 9 条（从 `coder-hard-constraints.md` 复制，含第 0 条"编码前 PRD+技术方案+任务文档+代码四方比对"）
- 本次任务特有的额外约束追加在末尾，标 "本次特有"
- 约束用祈使句，避免"建议/尽量/最好"等模糊词

### §3 上下文

#### §3.1 受影响文件清单

```markdown
| 文件 | 动作 | 备注 |
|------|------|------|
| `src/main/java/.../XxxServiceImpl.java` | 修改 | 在 `getUser` 方法中插入权限校验 |
| `src/test/java/.../XxxServiceImplTest.java` | 新增方法 | 新增测试 `shouldDenyAccessWithoutPermission` |
```

- 动作用"修改/新增/删除"，不用模糊词
- 路径用项目相对路径（从仓根起）

#### §3.2 关键依赖

列出本次编码涉及的关键符号，格式：

```markdown
- `PermissionChecker.check(String userId, String action): boolean` — 所在类 `com.xxx.util.PermissionChecker`
- `<DASHBOARD>BizException(ErrorCode code)` — 所在模块 `<DASHBOARD>-api`
- `ErrorCode.PERMISSION_DENIED` — 枚举值，位于 `com.xxx.common.ErrorCode`
```

#### §3.3 字段透传链路图（条件必须）

> **触发条件**：任务涉及字段透传/新增字段时必填，无字段透传可省略。

字段透传类任务必须绘制完整链路，确保每环都列入执行步骤，防止遗漏执行层：

```markdown
### 3.3 字段透传链路

`newField: String` 透传路径（入口 → 落库每一环）：

Req/Param（入口层）
  ├─ ✅ `XxxReq.newField` — Step 1 新增字段
  ├─ ✅ `XxxController.create()` — Step 2 接收
  └─ ↓
Service（执行层）⚠️ 易遗漏
  ├─ ✅ `XxxServiceImpl.processXxx()` — Step 3 赋值 stepPayload
  ├─ ✅ `CreateXxxHandler.setNewField()` — Step 4 setter
  └─ ↓
DAO/DB（落库层）
  └─ ✅ `xxxMapper.insert()` — 字段已在 SQL（无需改）
```

每环标注对应执行步骤编号，空白环（无 Step 编号）= 遗漏，Architect 必须在补全后再交付。

### §4 执行步骤

> **动作语义本规范自包含定义**（见下表），不依赖已删除的 `execution-plan-spec.md`。执行计划本身由 superpowers:writing-plans 产出，cdel 在此将其机读化为 Coder 任务文档的执行步骤。
>
> **与 superpowers 执行计划的衔接**：superpowers:writing-plans 产出的执行计划有自己的步骤格式，不一定含本规范的 4 字段（文件/定位/动作/代码）。Architect 在机读化阶段负责适配——消费 superpowers 执行计划时，若其步骤不含动作语义字段，Architect 根据 superpowers 的步骤意图补充动作字段（insert_after/before/replace/delete/new_file）+ 精确定位 + 完整代码块，转成 Coder 任务文档的 §4 执行步骤。即：superpowers 给"做什么+为什么"，cdel 补"具体怎么定位+怎么改"。

每条步骤必须包含 5 个字段：

| 字段 | 必填 | 格式 |
|------|------|------|
| **文件** | ✅ | 完整相对路径 |
| **定位** | ✅ | 方法名 + 行号或锚点描述（如"第 45 行 `return user;` 之前"） |
| **动作** | ✅ | `insert_after` / `insert_before` / `replace` / `delete` / `new_file` |
| **代码** | ✅ | 完整代码块（含正确缩进、import 如需要） |
| **核实** | ✅ | ✅ 已核实 / ⚠️ 未核实待 Coder 验证（见下方核实状态规则） |

**动作语义**：

| 动作 | 含义 |
|------|------|
| `insert_after` | 在定位点之后插入代码 |
| `insert_before` | 在定位点之前插入代码 |
| `replace` | 替换定位点的代码块 |
| `delete` | 删除定位点的代码块 |
| `new_file` | 新建文件（定位填"新文件"） |

**核实状态规则**（`核实`字段）：

- **✅ 已核实**：Architect 通过 `git show origin/<base>:<file>` 或直接读文件确认该行号/方法名/类名/API 用法真实存在
- **⚠️ 未核实待 Coder 验证**：Architect 因环境限制无法直接核实（如跨仓代码不可达、依赖未拉取），Coder 执行该步前先核实引用有效性；不匹配则触发硬约束第 3 条"计划偏差出口"
- **无 ✅ 标记的引用不得写入 coder-task**：Architect 不能把"印象中大概在 XX 行"的引用写入执行步骤
- 新建文件（`new_file`）步骤：核实状态填 `✅ 新文件`

**框架/组件 API 规则**：

- coder-task 涉及框架组件（如 antd、Element UI）时，代码块中的 API 必须**引用项目内现有用法锚点**（file:line），不能凭通用知识编写
- 示例：`` 组件 API 参考：`src/pages/UserEdit.tsx:128` 中 `TextArea` 使用 `autoSize`（非 `autosize`）+ `onChange(e => e.target.value)`（非 `onChange(val)`） ``
- 若项目中找不到现有用法参考，标 ⚠️ 并注明"建议 Coder 先验证 API 形态"

### §5 自测要求

- 编译命令：必须可直接运行（含模块路径 `-pl` 参数）
- 单测命令：必须指定测试类名
- 验收标准：编译 0 error + 所有单测 PASS（含新增 + 已有）

### §6 自审 checklist

8 条固定项，从 `coder-hard-constraints.md` 的"自审 checklist"段复制，逐条对应硬约束（含第 0 条四方比对）：

```
- [ ] 已完成 PRD+技术方案+任务文档+代码四方比对，无未标注分歧（已知分歧已确认以任务文档为准；技术方案问题已记录在报告）
- [ ] 编译通过，单测全绿
- [ ] 未修改本文档未列出的文件
- [ ] 未更改已有方法的签名
- [ ] 未引入新的外部依赖调用
- [ ] 输出中不含真实 token/姓名/邮箱
- [ ] 启动的进程已全部关闭
- [ ] 所有执行步骤已按顺序完成
```

### §7 输出要求

Coder 交付时须将完整报告**写入任务文档指定的文件路径**，写完即退出 session，**不回复"已写入 XX 文件"、不额外总结**。

报告文件路径写死在任务文档 §7：`<repo>/.claude/<slug>/coder/coder-report-<name>.md`

报告内包含 4 项：

1. **git diff** — `git diff` 的完整输出（脱敏后）
2. **自测结果** — 编译输出摘要 + 单测通过数（如 "15/15 pass"）
3. **自审 checklist** — §6 的 checkbox 完成状态（每项打勾或注明不通过原因）
4. **技术方案问题反馈**（条件：四方比对发现技术方案自身问题时必填） — 记录技术方案中的设计缺陷、步骤遗漏、逻辑矛盾等，供 Architect 裁决时修复技术方案。格式：
   - `{问题位置}`：`{问题描述}`，建议修复方向：`{X}`

**如实报告，不伪装通过**：自测/自审有任一项不通过，不能让报告看起来"全绿"——必须在该项下写明失败原因和已尝试的修复。Architect 审查时读报告文件，不依赖用户转发。
